# SDD 极简入门手册

> 「Spec 驱动开发」通俗指南，读完这份手册，你就能理解 SDD 是什么、为什么有用、什么时候用，以及立刻上手试一试。

---

## 一句话结论

**SDD（Spec-Driven Development，规格驱动开发）就是：动手写代码之前，先用大白话把「要做成什么样」写清楚，再让 AI 照着这份说明去写代码。**

一句话解释里有两个关键词：
- **Spec（规格说明）**：一份说清楚"要做什么"的文档。你可以把它理解成"给 AI 看的施工图纸"。
- **驱动**：意思是"以它为准"。代码由这份图纸决定，而不是拍脑袋边写边改。

如果你只记住一句话，那就是这句：**先说清楚要什么，再让 AI 去干。**

---

## 为什么需要 SDD？

想象你要装修房子，有两种方式：

**第一种：包工头直接开工。** 你只说了句"我想要个温馨的家"，工人就抡起锤子开始砸墙。砸到一半你说"哎不对，厨房要大一点"，再砸；贴完瓷砖你又说"这颜色太丑了"，返工重来。最后房子勉强能住，但处处别扭，你自己都说不清哪里出了错。

**第二种：先画图纸再施工。** 你和设计师坐下来，把每个房间的用途、尺寸、颜色、插座位置全画在图纸上。确认无误后工人照图施工。中途想改？改图纸，大家立刻知道影响到哪。

**第一种就是"凭感觉编程"（业界叫 Vibe Coding），第二种就是 SDD。**

用 AI 写代码时，"凭感觉"这种方式一开始特别爽——你说一句，AI 写一段，几分钟出一个功能。但几乎所有文章都记录了同一个真实故事：**爽感只能维持三个月左右。** 项目一大，AI 就开始"记不住"之前的约定，改了新功能又弄坏了旧功能，代码越堆越乱，最后没人敢动，只能推倒重写，众称："三个月墙"。

问题的根子只有一个，叫**"意图偏移"**，且模型能力越强，偏离意图的速度越快；
> 你脑子里想的 → 你说出来的 → AI 理解的 → AI 写出来的，一层层传下去，越传越歪。即：你说了一句话，AI 理解了 80%，推理了 120%，写出来的代码已经跑偏。

AI 有个特点：**它不会追问你"这个情况怎么处理"，它只会自己猜。猜对了是运气，猜错了就是 Bug。**

SDD 就是用来堵住"猜"的空间的。把要求写清楚，AI 就不用猜了。

## SDD 的本质（从第一性原理看）

招开所有花哨的名词，SDD 的本质其实是一个非常朴素的道理：

> **人负责想清楚"做什么"（WHAT），AI 负责搞定"怎么做"（HOW）**

为什么要这样分工？因为在 AI 时代，两件事的价值发生了对调：

- **过去**：写代码很慢很贵，"怎么实现"是核心难点。
- **现在**：AI 写代码又快又便宜，代码几乎可以"秒级重写"。真正值钱、也真正只有人能做的，是**想清楚到底要什么**。

微软有句评价特别精辟：**"SDD 是给你的思考做版本管理。"** 普通的代码管理，管的是代码怎么一步步变化；而 SDD 管的是**你的思考怎么一步步变清晰**——为什么做这个、边界在哪、做到什么程度算完成。

再往深一层，SDD 其实不是新发明。它的思想源头是软件行业几十年前就有的老智慧：**"先定义预期，再实现代码"**（这套思想有个家族叫 TDD/BDD，你现在不用记）。AI 时代只是让这个老道理重新变得无比重要。

**一句话记住本质：SDD 不让 AI 变得更聪明，它让 AI 变得更"可控"。先把意图外化为可验证的文字，再让 AI 照着做。**

## 核心流程（极简 4 步）

不管哪个工具、哪篇文章，扄掉外壳，核心都是这 4 步。你可以把它记成"**说清楚 → 定方案 → 拆任务 → 让它干**"。

### 第 1 步：说清楚要什么（Specify / 规格）
用大白话描述这个功能要做什么、边界在哪、做到什么样算成功。
> 一句话解释：告诉 AI 你的目标，而不是你的做法。

### 第 2 步：定技术方案（Plan / 设计）
让 AI 根据第 1 步，提出用什么技术、怎么设计。这一步 AI 起草，你审核。
> 一句话解释：AI 出方案，你来把关。

### 第 3 步：拆成小任务（Tasks / 任务）
把方案拆成一个个能独立完成、能独立检查的小任务清单。
> 一句话解释：把大象切成一口能吃下的小块。

### 第 4 步：让 AI 逐条实现（Implement + Validate / 实现）
AI 照着任务清单一个个写代码，每写完一个就打钩。最后**人一定要验收**。
> 一句话解释：照着清单施工，完工后必须验收。

📌 **重要提醒**：这 4 步不是"一次性写死"的瀑布流程。真实实践中，第 1、2 步经常要来回改 3-5 遍才靠谱。发现问题就回头改前面，这很正常，也是它最省钱的地方——**改一行文档，比改一百行代码便宜太多了。**

### 一张流程图看全貌
核心循环就这一个：Specify → Plan → Implement → Validate。**，内核相同——定义问题、拆解计划、执行编码、验证结果。
```
你的意图
   │
   ▼
┌──────────┐     ┌──────────┐     ┌──────────┐     ┌──────────┐
│ Specify  │────▶│   Plan   │────▶│Implement │────▶│ Validate │
│ (想清楚) │     │ (拆明白) │     │ (AI 执行)│     │ (人验收) │
└──────────┘     └──────────┘     └──────────┘     └──────────┘
       ▲                                                  │
       └──────────── 偏差反馈，修正 Spec ─────────────────┘
```

所有工具、框架、多步骤流程都是在这个循环的不同位置加强度——加模板让 Specify 更标准，加 Agent 让 Plan 更自动，加 CI/Harness 让 Validate 更严格。

## 什么时候该用 / 不该用（决策指南）

这是全套方法里**最重要的一节**。8 篇文章的作者几乎一致强调：**SDD 不是银弹，用错场景反而拖后腿。**

判断标准可以浓缩成一个简单公式：

> **任务复杂度 × 出错代价 × 是否要长期维护**

### ✅ 该用 SDD 的场景
- 功能复杂，要改好几个文件、好几个模块
- 需求有点模糊，需要先把话说清楚、和人对齐理解
- 在**已经上线的老项目**上加新功能（怕碰坏现有的东西）
- 需要**多人协作**，大家得有个共同的"契约"
- 这东西以后要**长期维护**，不是用完就扔

### ❌ 不该用 SDD 的场景
- 一句话能说清、只改 1-2 个文件的小需求
- 明确的小 Bug 修复
- 临时脚本、写着玩的 Demo、探索性验证
- 就算写错了，重来一遍也没什么损失的活儿

**一句话决策：小活儿、试验田 → 凭感觉快速干；大工程、生产系统、要维护 → 老老实实走 SDD。**

有位作者给了个很妙的比喻：**探索阶段像"谈恋爱"（凭感觉试），一旦决定"结婚"（正式开发），就得立字据（写 Spec）。**

## 实践要点（做到这几点就够了）

新手不用一上来就搞全套。抓住下面这几条，你就已经做对了 80%：

1. **从小功能开始练手。** 别拿最复杂的大功能试水，先用"加个删除按钮"这种小事熟悉流程。

2. **Spec 要具体、可测量。**
   - ❌ 坏例子："系统要快"（多快？谁知道）
   - ✅ 好例子："搜索响应时间控制在 200 毫秒以内"
   - 判断标准：**好的 Spec 是"能验证对错的"，坏的 Spec 是"怎么解释都行的"。**

3. **明确写出"不做什么"。** 告诉 AI 边界，比只告诉它要做什么更重要——否则它会自作主张加一堆你没要的东西。

4. **一个绝妙的检验方法**：问自己——"换一种技术来实现，这份 Spec 还成立吗？"
   - 如果你写了"用某某数据库的某某功能存排行榜"，换个数据库就失效了 → 说明你把"怎么做"混进了"做什么"，写细了。
   - 如果你写"排行榜要实时更新、延迟不超过 1 秒" → 用什么技术都成立 → 这才是对的。

5. **接受"多轮迭代"是常态。** AI 不会一次写对，就像新员工不会一次做对。你要在过程中不断指导它，而不是幻想一份完美 Spec 就能一劳永逸。

6. **验收环节绝不能省。** Spec 只保证"做对了方向"，不保证"每行代码都对"。有数据显示，无约束的 AI 代码里 **45% 含安全漏洞**，所以人工审查是最后也最重要的安全网。

7. **好 Spec 回答 6 个问题（模板速查）。** 写 Spec 卡壳的时候，把这 6 个问题过一遍就行：
   - 问题是什么？（一句话用户痛点）
   - 成功长什么样？（可量化的验收标准）
   - 用户故事是什么？（作为X，我想Y，以便Z）
   - 边界在哪？（明确列出"不做什么"）
   - 约束条件？（技术栈限制、性能要求）
   - 怎么验收？（判断"做完了且做对了"的方法）

8. **对成熟项目，加一条铁律：增量优先。** 隔离新增代码，不动已有逻辑。先把新功能写成独立模块，验证通过后再接入主流程——这能把"改坏老功能"的风险降到最低。

## 常见误区

这些坑，是多位作者用真实项目"踩"出来的血泪教训，看一眼能帮你少走很多弯路：

1. **过度规格化（写得比代码还细）。**
   把每个实现细节都规定死，Spec 就退化成了"用大白话写的代码"，AI 变成打字机，彻底失去意义。→ 用上面第 4 条的检验法自查。

2. **规格腐烂（文档没人更新）。**
   代码改了十几版，Spec 还停在第一版。新人照着看，理解的是另一个系统。→ 发现改动就顺手更新，别攒着。

3. **规格官僚化（改个按钮颜色都要走全套流程）。**
   团队被繁琐流程搞到怨声载道，最后干脆绕过流程，SDD 名存实亡。→ 大改动才走 Spec，小修小补直接改。

4. **虚假的安全感。**
   "我都写了这么详细的 Spec 了，AI 肯定写对了" → 放松了审查 → 埋下大雷。**Spec 替代的是需求文档，不是代码审查。**

5. **工具堆砌。**
   为了"做好 SDD"，装了一大堆工具，结果配置工具的时间比写代码还长。→ **一个 Markdown 文件 + 一个你已经在用的 AI，就够开始了。**

6. **误以为 Spec 比代码稳定（进阶反思）。**
   有作者实战后发现：很多关键决策是**写代码时才冒出来的**，前期 Spec 根本预见不到。硬要每次都先改 Spec 再改代码，一件 5 分钟的事要花 20 分钟。
   → **对存量老项目，现有代码本身就是最精确的"规格"。** 一句"参照某某文件来实现"，往往比写 500 字的 Spec 更管用。

7. **把 Spec 当成唯一的质量保障（进阶反思）。**
   真正保障质量的，除了 Spec，还有更持久的"护栏"：给 AI 看的项目说明书、类型检查、自动化测试、代码审查。这套组合有个名字叫 **Harness Engineering（约束工程）**——不预测你要做什么，只保证"不管怎么做，我都能检查出对不对"。**Spec 赌的是"输入完美"，Harness 建的是"验证完善"，后者更贴近工程现实。**

> 💡 划重点：前 5 个是入门必避的坑，后 2 个是"用过一阵后"的深度反思——它们不是否定 SDD，而是提醒你：**Spec 是有用的思考工具，但别把它当成万能药。**

## 工具概览

市面上工具不少，新手记住下面这几个主流的就够了，按"适合谁"来选：

| 工具 | 谁做的 | 一句话特点 | 适合谁 |
|---|---|---|---|
| **Spec Kit** | GitHub | 最流行、通用、不绑定任何 AI，一套清晰的模板流程 | **新手首选**，想通用、想学标准流程 |
| **OpenSpec** | Fission-AI | 轻量、灵活，把每次改动当成一个"提案"来管理 | 个人开发者、快速小步迭代 |
| **Kiro** | AWS | 一个"开箱即用"的智能开发工具（IDE），SDD 流程内置好了 | 想省心、不想自己搭环境的人 |
| **Qoder / QoderWork** | 阿里 | 阿里内部的执行引擎，那个"5 人 7 天"案例就用的它 | 阿里体系内的团队 |

配套还会听到几个词，简单知道即可：
- **Constitution（宪法）**：项目的"铁律"，比如"必须写测试""不准硬编码密码"，所有 Spec 都得遵守。
- **Skills（技能包）**：把团队经验、规范打包成 AI 能随时调用的"外挂知识"。
- **CLAUDE.md / AGENTS.md**：给 AI 看的"项目说明书"，告诉它"在这个项目里怎么做事才对"。多位作者认为这玩意儿比 Spec 更有长期价值。

**新手建议：直接从 Spec Kit 开始，别纠结选型。**

## 一个最小可行示例（立刻能试）

下面是让你 10 分钟内跑通全流程的最简单例子。假设你用的是 Spec Kit + 一个 AI 编程工具（如 Claude Code）。

### 准备（只做一次）
```bash
# 安装 Spec Kit（需要先装好 Python 环境）
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git

# 进入你的项目目录，初始化
specify init .
```

### 四步走一遍
```bash
# 第 1 步：说清楚要什么（用大白话描述需求）
/speckit.specify 我要一个用户注册功能，输入邮箱和密码，邮箱格式要校验，密码至少8位

# 第 2 步：AI 出技术方案（你审一下生成的文档，不满意就改）
/speckit.plan 用 React 来实现

# 第 3 步：拆成可执行的小任务清单
/speckit.tasks

# 第 4 步：让 AI 照着清单逐条实现
/speckit.implement
```

### 更简单的"零工具"版本
如果你连工具都不想装，其实 **SDD 的精髓一个记事本就能实践**：

1. 新建一个文件 `spec.md`，用大白话写清楚：
   ```markdown
   # 功能：用户注册
   ## 要做什么
   用户输入邮箱和密码完成注册
   ## 成功标准（可验证）
   - 邮箱格式不对时，提示"邮箱格式错误"
   - 密码少于8位时，提示"密码太短"
   - 注册成功后返回用户ID
   ## 不做什么
   - 本期不做第三方登录
   - 本期不做手机验证码
   ```
2. 把这个文件丢给任意 AI，说："请严格按这份 spec 实现代码。"
3. AI 写完，你对着 spec 逐条验收。
4. 要改需求？先改 spec，再让 AI 重新生成。

**就这么简单。** 你已经在做 SDD 了。剩下的，都是熟练度问题。

## 三条铁律 

1. **Spec 是给 AI 看的，不是给领导看的。** 写得让 AI 能无歧义执行，比写得漂亮重要。别追求"文档好看"，追求"AI 看完能做对"。

2. **Spec 不等于一次写完。** 第一版 60 分就够，执行中发现偏差再迭代。过度前置设计反而浪费——你不可能在没写代码之前就预见所有细节。

3. **验证比生成重要。** AI 生成代码的成本趋近于零，验证代码正确性的成本不会趋近于零。把精力放在验证环节，而不是幻想一份完美 Spec 就万事大吉。

## 基本共识
- **先想后做，Spec 先行。** 所有文章都认同：不管叫 spec.md、Gherkin、constitution 还是 Project Rules，开工前必须有一份外化的意图文档。
- **AI 不替代人类判断。** Spec 只是让 AI 可控，最终的架构决策、边界取舍、质量验收仍然依赖人。
- **文档即资产。** Spec/Plan/Tasks 组成的文档集是项目的长期知识沉淀，不是用完就丢的一次性产物（即使批评者也认同"约束"本身有持久价值）。
- **适用场景有边界。** 单文件改动、bug 热修、临时脚本不需要 SDD，高投入只值得用在多模块/多人/长期维护的场景。

## 一些分歧
| 争论轴 | 一方观点 | 另一方观点 |
|--------|---------|-----------|
| **约束放在哪** | 前置 Spec 文档，写清楚再动手 | 运行时约束（类型系统+CI+Git Hooks）比 Spec 更可靠 |
| **Spec 的寿命** | 是持久的"唯一真理源"，随代码同步更新 | 是一次性消耗品，实现后真正的约束活在代码和工程管线里 |
| **个人 vs 团队** | SDD 本质是个人效率工具，团队协同靠流程补 | 必须升级为分层 Agent 架构才能解决多仓多人协调 |
| **正式程度** | 越严格越好，要写验收标准、非目标、约束条件 | 过度规约会变成"Spec 官僚主义"，根据任务大小调深度 |
| **终极愿景** | Spec 即源码（代码成为衍生物） | Spec 只是过渡，模型足够强后可以"直接聊" |

## 结语

SDD 的核心，其实就是那句从几十年前流传至今的老话：**"先想清楚，再动手。"**

区别只在于——过去你是把需求讲给同事听，现在是讲给 AI 听。而 AI 比人更"较真"、更不会追问，所以你得讲得更清楚。

别追求完美，从一个 `spec.md` 文件、一个你熟悉的 AI 开始，从一个人、一个小功能起步。用几次你就会有感觉了。

> **DAY 0 花时间想清楚的那一天，看似什么都没干，其实是最值的一天。**
