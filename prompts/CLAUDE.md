# 项目编码约定

总则:稳定性优先于一切。下列规则由历史改动中反复出现的具体要求反推为通用原则,适用于所有项目与编码场景;拿不准时,选影响面最小、最可逆、最少惊喜的那种做法。

## 稳定性与变更边界
- **与现状/契约/文档冲突时,先确认再动手**:任务要求和代码现状、接口契约、既有文档相抵触时,停下说明冲突并给出可选项,不替决策方擅自选一种改法。
- **改动最小且可逆**:优先影响面最小的实现;能不动的对外接口/数据契约/公共签名就不动,非改不可先评估下游影响。
- **顺带改动显式声明,不静默夹带**:为跑通任务必须捎带的修复(如挡编译的既有问题)单独说清来龙去脉;与本次目标无关的改动不混进同一次提交。
- **契约/行为变更同步更新文档**:改了对外接口、字段、枚举语义,同步更新接口文档与相关说明文档,不留 stale 描述——与「测试同步」同理。

## 注释规范
显而易见的代码本身就是最好的注释。写注释前先问:能靠重构或命名消掉它吗?能就别写。

- 一条注释只承担三者之一,优先级 **干什么 > 怎么做 > 为什么**。
- **函数文档只写「干什么」的一句话摘要,不逐行复述内部直线实现**:参数如何流转、先做 A 再做 B、哪个分支返回 nil——这些读代码就懂的直线逻辑不写进文档注释;能靠函数名/参数名/返回类型自解释的更不写。真正非显而易见的「为什么」(顺序约束、契约边界、坑)才值得单独一行,且宁可用代码结构表达也不靠注释维持。
  - 反例:`// 先写入按 detailId 索引的算法决策,再基于决策关联的资源位 id 加载文案变量。文案取自决策产物,故顺序不可颠倒,全程降级不阻断……`(把函数体又用中文说了一遍)
  - 正例:`// preloadAmpDecisionContext 预加载 AMP 执行所需的中间结果:算法决策与其关联的触达文案变量。`
- **禁止过渡性/过程性注释**:如"首先…""接下来…""这里我们…""初始化 xxx""调用 yyy 处理"——这类复述代码的话一律不写;调用点上方复述被调函数名的「段落标记注释」(如 `// 参数验证` 之于 `validateExecuteRequest()`)同样删掉,函数名即注释。
- 常量/变量的注释描述其**内容**,而非用途。
- **禁止内部规划编号**:注释里不写 `RL-x`、`T-x`、`design §x` 这类只在设计文档/任务清单里有意义的编号——规划一改即成死引用,要表达就写成自解释的白话。
- 烂代码不写注释解释,直接重构;宁可重构一段代码,也不要给它加注释。
- 公共 API:不显而易见或不够简短的必须注释;库中的函数无论长短都注释;**例外**:实现接口的方法不重复注释。

## 命名与表达
- **业务判断用显式信号,不从别的字段取值反推**:给「满足某条件的一类东西」一个自己的字段/集合,别让人从 `if level == 1` 猜出「这是特征项」。反例:靠 `x == 常量A` 间接代表一层语义;正例:自解释的布尔/集合直接表达。
- **判定优先用内在标识,不用枚举代理**:实体自带直接标识(如关联 id)就用它,别用「来源/类型枚举 == 某值」这种要靠写侧不变量维持、易漂移的间接信号。

## 代码结构
- **对称扩展要完整复制既有那一支**:新增与既有并列的分支/标记/常量时,既有那支走过的处理路径(常是生成侧 + 校验侧两端)新增的都要走全,别只做「半覆盖/排除式」变体。
- **被剔除/降级/跳过的数据不静默丢弃**:分支里丢掉的东西要么有显式规则、要么留日志,别靠某次调用的执行顺序隐式决定其命运。
- **重命名/替换旧概念要对称清理**:旧名、旧枚举值的所有引用(代码、注释、文档、示例、测试)一并改净,不留半新半旧的孤儿引用——与「对称扩展」互为正反。
- **新增同类代码照抄既有已验证的写法**:import 路径、类型选择、字段来源都对齐就近的既有实现,不另起一套等价方案。

## 依赖与外部契约
- **用外部符号前先读它的真实定义**:三方包/其他模块的常量名、类型、字段、序列化 tag,一律以源码为准核对后再下笔,不凭记忆或推测。
- **改序列化契约要读写两端一致**:改了字段名/类型/枚举语义,写侧、读侧、Mock、示例同步改全,别只改一端留下反序列化裂缝。

## 引用与定位
- **引用代码位置用「文件 + 符号名」,不写绝对行号**:理由同「禁止内部规划编号」——代码一增删行号即成死引用。正例:`xxx.go 的 FooBar`;反例:`xxx.go:275`。

## 测试
- **行为变更与测试在同一次改动里提交**:改了逻辑就同步改断言,不留与现码矛盾的 stale 用例。
- **非平凡逻辑(分支/循环/钱路径/安全路径)至少留一个可跑校验**;平凡一行不必测。
- **改动后必须自证**:编译通过且相关测试跑绿才算完成;跑测试的环境前置(特定编译/运行参数等)一并记录,不把环境问题误报成代码结论。

# SDD（规格驱动开发）文档准则

功能规格存放于项目的 `.claude/specs/<功能>/`。核心循环:**说清楚 → 定方案 → 拆任务 → 让它干**,并在偏差处回头修规格——**改一行文档比改一百行代码便宜**。

## 四步循环（Specify → Plan → Implement → Validate）

1. **Specify（规格 / WHAT）**:用大白话说清做什么、边界在哪、怎样算成功。告诉目标,不是做法。
2. **Plan（设计 / HOW）**:据规格提技术方案,AI 起草、人审核。
3. **Tasks（任务）**:拆成能独立完成、独立验收的小任务清单。
4. **Implement + Validate（实现 + 验收）**:照清单逐条实现、打钩;**完工人必须验收**。

非瀑布:第 1、2 步常来回改 3-5 遍,发现问题就回头改前面——这正是它最省钱的地方。偏差反馈永远指回修正 Spec。

## 文档分层与「实现细节」边界

| 文档 | 层 | 对「函数名/变量名/类型名/字段名/接口路径/框架 API」的要求 |
|------|----|-----------------------------------------------------------|
| `requirements.md` | Spec / WHAT | **严禁出现**。只用行为与可量化验收表达,须通过「换技术自检」 |
| `design.md` | Plan / HOW | 描述架构/职责/数据流/失败处置;优先用角色与行为表达,尽量少绑具体符号名 |
| `tasks.md` / `verification.md` / `PROGRESS.md` | 实现层 | 以「交付了什么能力、如何验证」表达,减少对具体符号的强耦合 |

## 硬规则

1. **具体、可测量**:❌「系统要快」 ✅「搜索响应 ≤ 200ms」。判据——**好规格能验证对错,坏规格怎么解释都行**。
2. **写清「不做什么」**:明确边界比只说要做什么更重要,否则 AI 自作主张加一堆你没要的。
3. **换技术自检**:问自己「换一种技术来实现,这份 Spec 还成立吗?」成立才对。把「怎么做」混进「做什么」,就是写细了。
4. **接受多轮迭代是常态**:AI 不会一次写对,要在过程中持续指导,别幻想一份完美 Spec 一劳永逸。
5. **验收环节绝不能省**:Spec 只保「方向对」,不保「每行代码对」。人工审查是最后也最重要的安全网。
6. **存量项目增量优先**:隔离新增代码、不动老逻辑,独立验证通过后再接入主流程,把「改坏老功能」的风险降到最低。
7. **存量项目里,现有代码本身就是最精确的规格**:一句「参照某某文件实现」常胜过 500 字 Spec。

## 好规格答 6 个问题（模板速查）

问题是什么(一句话痛点)/ 成功长什么样(可量化验收)/ 用户故事(作为 X,想 Y,以便 Z)/ 边界(明确「不做什么」)/ 约束(技术栈、性能)/ 怎么验收(判定「做完了且做对了」的方法)。

## 常见误区（避坑）

1. **过度规格化**:细到成「用大白话写的代码」,AI 沦为打字机 → 用规则 3 自检。
2. **规格腐烂**:代码改了十几版,文档停在第一版 → 发现改动就顺手更新,别攒着。
3. **规格官僚化**:改个按钮颜色也走全套流程 → 大改动才走 Spec,小修小补直接改。
4. **虚假安全感**:「写这么详细 AI 肯定对」→ 放松审查埋雷。**Spec 替代需求文档,不替代代码审查**。
5. **工具堆砌**:配工具比写代码还久 → 一个 Markdown + 一个在用的 AI 就够起步。
6. **误以为 Spec 比代码稳定**:很多关键决策写代码时才冒出、前期预见不到 → 存量项目「参照某文件」更管用。
7. **把 Spec 当唯一质量保障**:真正持久的护栏是项目说明书 + 类型检查 + 自动化测试 + 代码审查(Harness/约束工程)——不预测你要做什么,只保证「不管怎么做都能验出对错」。
